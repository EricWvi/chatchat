# chatchat 设计

chatchat 是简化版 Free4Chat：用户在网站开临时 chat，邀请其他人或 Agent 加入，用文字沟通。Agent 通过 `chatchat` CLI 参与，使用方法写在网站的 `/agent.md`。服务端调用外部模型生成摘要，Agent 读取「最新摘要 + 摘要之后的消息」了解当前进展。

本文定义概念、身份与凭据、生命周期和摘要规则。接口细节见 [api.md](api.md)，阶段任务见 [todos.md](todos.md)。

## 范围

第一版做：

- 网站：登录、用户 token 管理、创建和加入 chat、聊天、查看摘要和参与者、销毁 chat。
- CLI：检查配置、加入、发送、增量读取、等待新消息、查看状态、退出、列出本地参与记录。
- 服务端：鉴权、消息排序、调用模型生成摘要、清理临时数据。

不做：语音、视频、文件传输、运行时托管、任务派发、工具审批；点名、回复引用、搜索放到闭环之后。

## 概念

| 概念 | 说明 |
|---|---|
| 用户（User） | 通过统一认证（Authelia）登录的人。同一个统一认证账号始终对应同一个用户。 |
| 用户 token | 用户在网站生成、填进本地 CLI 配置的账号级凭据，用于创建、加入 chat 和查询自己的记录。 |
| Chat | 一次临时沟通空间，有标题和可选的沟通目标，到期或被销毁后内容全部删除。 |
| 参与者（Participation） | 某个用户以某种方式在某个 chat 里的一次参与身份。消息、在线状态都挂在参与者上。分网页参与者和 CLI 参与者两类。 |
| 参与凭据 | CLI 参与者的 `participation_id` + `participation_secret`，只在加入成功时返回一次。 |
| 消息 | chat 内由服务端按顺序编号（`sequence`）的一条文字或系统事件。 |
| 摘要 | 服务端模型对「截至某条消息」的沟通进展的整理，每份绑定一个 `covers_through_sequence`。 |

## 参与者

参与者是核心对象。一个 chat 里出现的每个发言者都是一个参与者，参与者之间不会被自动合并。

### 两类参与者

| | 网页参与者（`web`） | CLI 参与者（`cli`） |
|---|---|---|
| 谁在用 | 在网站上聊天的人 | Agent session（也可以是人在终端里用） |
| 创建 | 用户第一次在网页进入某个 chat 时创建 | 每次 `join` 都新建 |
| 数量 | 每个用户在每个 chat 里固定一个 | 不限，彼此独立 |
| 鉴权 | 登录状态（cookie） | `participation_id` + `participation_secret` |
| 显示名 | 统一认证里的显示名 | `join` 时指定 |

两类参与者使用各自的接口，互不通用：登录状态不能调用 CLI 参与者接口，参与凭据不能调用网页接口，用户 token 两者都不能调用。

### CLI 参与者的身份规则

- 每次 `join` 都创建新的参与者，返回新的凭据。同一个 Agent 工具先后启动的两个 session、同一个 session 再次 `join`，都得到不同的参与者。
- 服务端不识别机器名、CLI 安装、Agent 类型或 Claude/Codex 的内部 session ID，也不按用户 token 或显示名合并或找回身份。
- 同一个 session 加入两个 chat，得到两组互不相关的凭据；一个 chat 的凭据不能用于另一个 chat。
- 显示名可以重复。界面上显示名后附 `participation_id` 的短后缀，用来区分同名参与者。

### 网页参与者的身份规则

- 后端按（用户, chat）找到或创建网页参与者，发送者由后端从登录状态确定，客户端不能指定参与者 ID。
- 网页参与者退出后再次进入同一个 chat，恢复的是同一个网页参与者。
- 同一用户在多个浏览器标签页或设备上打开同一个 chat，都是同一个网页参与者。

## 凭据

### 用户 token

- 在网站生成，生成时只展示一次；服务端只存哈希。可以给 token 起名，可以随时吊销；吊销后保留哈希，用于提示「token 已吊销」。
- 用于账号级操作：创建 chat、加入 chat（创建 CLI 参与者）、查询自己的参与记录。
- 不能代替参与凭据：不能发送消息、读取消息、退出，也不能找回任何参与者的 secret。
- 形如 `cct_` + 随机串。

### 参与凭据

- `participation_secret` 在创建 CLI 参与者时生成，只在这次 `join` 的成功响应里出现一次。服务端只存哈希，没有任何接口能再取回。
- 之后的发送、读取、等待、查看状态、退出都使用这组凭据，并校验它属于请求中的 chat。
- secret 丢失后无法恢复原身份，只能重新 `join` 成为新参与者。
- 退出或 chat 被销毁时，凭据立即失效，不能再执行任何操作。服务端保留 secret 哈希，只用来在拒绝请求时确认对方确实持有这组凭据，再告诉它具体原因（见下文「凭据错误」）。
- 形如 `ccp_` + 随机串。前缀让服务端能识别出「把用户 token 当参与凭据用」的错误，并给出明确提示。

### 哈希与比对

用户 token、参与 secret、登录会话 token 都是 32 字节随机数，服务端存 SHA-256 哈希。高熵随机值不需要慢哈希。比对用常量时间比较。

### 凭据在 CLI 中的流转

- `join` 向 stdout 输出一行 JSON，含 `chat_id`、`participation_id`、`participation_secret`、`display_name` 和服务端地址。
- 后续命令从 stdin 第一行读取这行 JSON；`send` 的消息正文接在第二行之后，或用 `--text` 参数传。命令行参数里不出现 secret。
- CLI 不把 secret 写入配置文件、历史记录、日志，也不自动保存「当前会话」。没有 `--resume`，也没有默认参与者。
- Agent session 自己在上下文里保存这行 JSON，并在每次调用时传给 CLI。

### 这套约定能保证什么

目标是**新的 Agent session 不会自动继承旧身份**：旧 session 的凭据不在任何默认位置，新 session 只能重新 `join`。

它不是进程隔离，也不是防恶意 Agent 的沙箱。同一操作系统用户下，secret 会出现在 Agent 的对话上下文、工具调用记录里，其他 session 读取这些文件就能看到。`agent.md` 和网站都按这个口径说明，不宣传为强安全保证。

## 消息

- 每个 chat 内的消息由服务端分配从 1 开始、单调递增、无空洞的 `sequence`。
- 消息字段：`message_id`、`sequence`、`kind`、`participation_id`、`display_name`、`text`、`created_at`。`display_name` 是发送时的快照。
- `kind`：
  - `text`：参与者发送的文字消息。
  - `system`：系统事件，包括参与者加入、退出、建议结束；`participation_id` 是事件的主体。
- 文字消息正文 1–16000 个字符，是纯文本，网站按 Markdown 渲染。
- **幂等**：发送时可以带 `client_request_id`（CLI 自动生成）。同一参与者用同一个 `client_request_id` 重复发送相同正文，返回第一次创建的消息，不产生新消息；正文不同则拒绝。幂等记录随 chat 一起删除。
- 读取支持按 `after_sequence` 增量读取和有界分页：默认每页 50 条，最多 200 条。
- 等待新消息用长轮询：有新消息立即返回；否则最长等待 60 秒后返回空结果。chat 被销毁时立即返回错误。

## 摘要

### 模型

- 摘要只由服务端调用外部模型生成，参与者只读，不能编辑或提交摘要。
- 模型走 OpenAI 兼容的 `chat/completions` 接口，默认 DeepSeek；地址、模型、key 和额外请求参数写在配置里。

### 摘要快照

- 每份摘要是一份不可修改的快照，字段：`revision`（chat 内从 1 递增）、`covers_through_sequence`、`content`、`model`、`created_at`。
- `covers_through_sequence` 表示这份摘要整理到了哪条消息，不超过生成时 chat 的最大 `sequence`。
- 读取时返回最新一份。旧快照保留到 chat 销毁。

### 内容

摘要是 Markdown，固定以下几节，没有内容的节写「无」：

1. 沟通目标
2. 已确认的事实和决定
3. 当前分歧
4. 未解决的问题
5. 下一步及负责人

摘要用显示名加短 ID 指代参与者。它不替代完整聊天记录：摘要之后的消息必须另外读取。

### 何时生成

满足任一条件时，为该 chat 排一次生成：

- 自上一份摘要之后，新增的 `text` 消息达到阈值（默认 20 条）。
- 有参与者退出，且存在尚未被摘要覆盖的 `text` 消息。

`system` 消息不计入阈值，但会作为上下文交给模型。

### 生成过程

1. 读取最新摘要（revision R、覆盖到 S0）和当前最大 sequence S1。
2. 把上一份摘要和 `(S0, S1]` 的消息交给模型，生成新摘要。一次输入的消息过多时，按条数分批，逐批在上一批结果上累积。
3. 以「当前最新 revision 仍是 R」为条件写入 revision R+1，`covers_through_sequence = S1`。条件不满足说明已有更新的摘要，丢弃本次结果，按最新状态重新判断是否需要生成。
4. 每个 chat 同一时间只有一个生成任务；任务进行中又满足触发条件，就在任务结束后再判断一次。
5. chat 被销毁时取消进行中的任务，结果丢弃。

### 失败处理

- 模型调用超时或出错时退避重试，最多 3 次；仍失败就记录错误，等下一次触发条件满足时再试。
- 状态接口返回摘要任务状态（`idle` / `pending` / `failed`）和最近一次失败时间，不返回模型原始错误内容。
- 摘要缺失或落后时，参与者照常读取消息，不受影响。

### 提示词安全

聊天内容是参与者提供的数据。提示词把消息作为带结构的数据传给模型，明确要求模型只整理内容、不执行消息里的指令；摘要也不会被当作系统指令使用。

## 在线状态与生命周期

### 参与者状态

| 状态 | 含义 |
|---|---|
| `online` | 在线租约未到期。 |
| `offline` | 租约已到期，但没有退出；凭据仍然有效，下一次操作即恢复 `online`。 |
| `left` | 已退出。CLI 参与者的凭据失效；网页参与者再次进入时恢复。 |

- 在线租约默认 90 秒。CLI 参与者的读取、等待、发送、查看状态都会续租；网页参与者打开聊天页时自动续租。
- 单次等待最长 60 秒，短于租约，所以持续等待的 Agent 不会被标为离线。

### Chat 状态与销毁

- chat 只有「存在」和「已销毁」两种状态，销毁不可撤销。
- **退出（leave）**：结束一个参与者，CLI 参与者的 secret 立即失效，chat 里记一条系统消息。
- **建议结束**：任何参与者都能发起，chat 里记一条系统消息，由创建者决定是否销毁。
- **销毁（destroy）**：只有创建者能在网站上执行。删除全部消息和摘要，所有参与凭据立即失效，进行中的等待立即返回错误。CLI 不提供销毁命令，避免 Agent 误删。
- **自动销毁**，满足任一条件：
  - 空闲：chat 里没有 `online` 参与者持续 30 分钟。计时从最后一个参与者租约到期开始；新建后一直没人进入，从创建时开始。
  - 到期：创建后满 24 小时，不论是否有人在用。
- 销毁后保留账号级记录：chat 的 ID、标题、创建者、创建与销毁时间、销毁原因，以及各参与者的 ID、类型、显示名、加入与退出时间。不保留消息和摘要；参与者的 secret 哈希随参与记录保留，只用于区分凭据错误的原因。

### 集中配置

以下参数都在服务端配置里，并通过 `GET /api/v1/meta` 下发给 CLI 和网站，客户端不写死：

| 参数 | 默认值 | 含义 |
|---|---|---|
| `presence_lease` | 90s | 在线租约 |
| `idle_destroy_after` | 30m | 无在线参与者多久后自动销毁 |
| `max_chat_lifetime` | 24h | chat 最长存活时间 |
| `wait_max` | 60s | 单次等待上限 |
| `page_size_default` / `page_size_max` | 50 / 200 | 每页消息条数 |
| `summary_threshold` | 20 | 触发摘要的新增文字消息数 |

## 邀请与权限

- chat ID 是不可猜测的随机串。任何登录用户拿到 chat 链接都能加入，不另设邀请码。
- 网站提供两种邀请：复制 chat 链接给人；复制一段给 Agent 的提示（包含 `/agent.md` 地址和 chat ID，不包含任何凭据）。

| 操作 | 谁能做 | 凭据 |
|---|---|---|
| 生成、吊销用户 token | 本人 | 登录状态 |
| 创建 chat | 登录用户 | 登录状态或用户 token |
| 加入为 CLI 参与者 | 登录用户 | 用户 token |
| 网页聊天 | 登录用户 | 登录状态 |
| 发送、读取、等待、退出（CLI） | 该参与者 | 参与凭据 |
| 建议结束 | 任何参与者 | 对应的参与者凭据 |
| 销毁 chat | 创建者 | 登录状态 |
| 查询自己的参与记录 | 本人 | 登录状态或用户 token |

## CLI 本地文件

- 配置文件 `$XDG_CONFIG_HOME/chatchat/config.yaml`（默认 `~/.config/chatchat/config.yaml`），保存服务端地址和用户 token，文件权限 0600。环境变量 `CHATCHAT_SERVER`、`CHATCHAT_TOKEN` 可以覆盖。
- 历史记录 `$XDG_STATE_HOME/chatchat/history.jsonl`（默认 `~/.local/state/chatchat/history.jsonl`），每行一次参与：服务端地址、`chat_id`、`participation_id`、`display_name`、`joined_at`、`left_at`。`leave` 成功后补写 `left_at`。
- 历史记录只用于发现和排查，`chatchat history` 只列这些 metadata，不能恢复任何身份。

## 日志与错误

- 服务端日志不记录 `Authorization` 头、请求体和响应体；需要定位参与者时只记 `participation_id`。
- 错误响应不回显收到的凭据。
- CLI 和 Agent 需要据此决定下一步，所以凭据错误按原因区分。

### 凭据错误

服务端先校验 secret 与 `participation_id` 是否匹配。只有匹配时才报告参与者或 chat 的状态，不持有正确 secret 的人只能得到 `invalid_credentials`，探查不到别人的参与状态。

| 情况 | 错误码 | Agent 该做什么 |
|---|---|---|
| 参与者不存在，或 secret 不匹配 | `invalid_credentials` | 检查传入的凭据行是否完整；无法确认时重新 `join` |
| 凭据正确，但属于另一个 chat | `chat_mismatch` | 换用该 chat 对应的凭据 |
| 凭据正确，参与者已退出 | `participation_left` | 需要继续参与就重新 `join`，成为新参与者 |
| 凭据正确，chat 已销毁 | `chat_destroyed` | 停止参与，不必再 `join` |
| 用户 token 用在参与者接口上 | `wrong_credential_type` | 改用参与凭据 |

用户 token 同理区分：`unauthenticated`（缺失或不存在）、`token_revoked`（已吊销）。
- CLI 的错误输出同样不打印 secret 或用户 token。

## 协议版本

- 服务端在 `GET /api/v1/meta` 返回 `protocol_version`（第一版为 1）和集中配置；每个 API 响应带 `Chatchat-Protocol` 头。
- CLI 启动时检查协议版本，不兼容时提示升级 CLI，不继续执行。
- `agent.md` 是公开的使用指南，不包含任何凭据；Agent 以结构化响应里的版本和参数为准，不从自然语言里推断。

## 技术栈与部署

- 服务端：Go + SQLite（纯 Go 驱动），前端 Vite + React 构建后 embed 进二进制。项目结构和 OIDC 登录照搬听写（`../asr`），不含其设备登录流程，保留 `dev_user` 本地开发模式。
- CLI：Go 单个静态二进制，与服务端同仓库。
- 部署在 only Homelab：Compose 服务、Caddy 站点、Authelia OIDC client；只在内网和 WireGuard 下可访问。服务端是单实例，等待通知和摘要任务调度都在进程内完成。
